# Production Deltas

This ledger records every place where the interview build deliberately takes a simpler path than a production system would. Each row states what was built, what production would require, why the simpler path was chosen, and how the production version would be reached. Rows are added as decisions are made, not retroactively.

The guiding rule from the blueprint: demo-visible correctness (idempotent ingestion, null-tolerant parsing, evidence preservation, deterministic compliance, secrets hygiene) is never cut; invisible infrastructure may be simplified when documented here.

| # | Area | What the demo does | What production would do | Why deferred | Migration path |
|---|---|---|---|---|---|
| 1 | Authentication | Django's built-in `User`; one superuser created manually with `createsuperuser` (username = demo email); credentials shared with the reviewing team | Custom user model with email as `USERNAME_FIELD`, self-service accounts, roles, MFA/SSO | Exactly one account exists; account machinery has no demo value | New `AUTH_USER_MODEL` requires a fresh app or a data migration; roles map onto the existing single-actor audit fields |
| 2 | Demo-user creation | Non-idempotent manual command, run once per environment | Idempotent provisioning (management command or IaC) from environment credentials | One environment, one account, one run | Wrap `createsuperuser` in an idempotent `ensure_demo_user` command |
| 3 | Per-stage processing audit | `IngestionJob` carries a single status, retry count, and last error; stage detail lives in logs, `AIOperation`/`AIProviderCall`, and Langfuse | A normalized per-attempt table (job, stage, attempt, provider metadata) powering a per-stage progress UI with per-stage retry | The PRD defers the per-stage UI to P1; the table's only consumer does not exist in P0 | Reintroduce the attempt table alongside the P1 per-stage UI; append-only design means no backfill is required |
| 4 | Live simulation | Designed in [Step 2F](./specs/step-2-domain-model.md#9-step-2f--simulation-p1-ai-metrics-cost-and-evaluation) but not built in P0; the live demonstration is the Manual Ingestion Lab | Scripted, resettable event-replay simulation with its four dedicated tables | PRD classifies the simulator as P1 and forbids it delaying the core product | Create the P1 migrations from the recorded design; `simulation_run` columns are nullable additions |
| 5 | Duplicate audio detection | SHA-256 over uploaded bytes: the identical file is caught; a re-encoded copy of the same call is not | Content-level audio fingerprinting robust to re-encoding | Signal-processing work with near-zero demo value | Add an acoustic fingerprint column beside the byte checksum |
| 6 | Duplicate-path hardening | Fingerprint column and unique constraint ship in the initial migration; duplicate-path UX polish and dedicated tests are scheduled after the end-to-end happy path works | Duplicate handling tested as a first-class flow from day one | Sequencing decision: foundation and happy path first | The constraint already enforces correctness; only tests and UX copy are added later |
| 7 | Seed determinism | Re-running seed is idempotent by record identity, but a wipe-and-reseed re-runs LLM extraction, whose field values may vary between runs | Replay mode re-applying stored validated provider outputs; pinned sampling parameters | Accepted for a demo that seeds once per environment | The append-only `ExtractionRun`/`Transcript` rows already preserve everything a `seed --replay` needs |
| 8 | Stuck-job recovery | Celery task time limits plus one bounded global sweep across all stale processing jobs whenever any job is polled or seed health is summarized | A scheduled reaper (Celery Beat or cron) independent of UI and operator traffic | Celery Beat is excluded from P0; polling and deploy-day seed checks provide sufficient demo triggers | Move the same global sweep service into a Beat/cron task unchanged |
| 9 | Audio delivery | Streamed through an authenticated Django endpoint in all environments | Signed URLs or a CDN in front of object storage for scale | One code path that works identically locally and deployed; demo traffic is a single user | Swap the endpoint for signed-URL generation behind the same storage abstraction |
| 10 | Bucket networking | Railway Storage Bucket reached over its public S3 endpoint with credentials (Railway offers no private-network bucket access yet) | Private networking or VPC endpoints to object storage | Platform limitation; the bucket itself is access-private | Adopt private endpoints when the platform (or a different store) provides them |
| 11 | Prompt release window | The bundled fallback prompt may briefly lead the Langfuse `production` label between merge-deploy and promotion | Release gating so deployed fallbacks never precede evaluated promotion | Single author, ~3 prompts; the window is minutes and self-inflicted | Promote in Langfuse before merging, or gate the merge on promotion |
| 12 | Langfuse payload capture | A deployment setting (`LANGFUSE_CAPTURE_PAYLOADS`) controls whether prompt inputs/outputs are captured; enabled for the interview demo so the reviewer can inspect extraction, tool, and drafting behavior (satisfies PRD 12.4) | Field-level masking and redaction granularity within captured payloads, not just an all-or-nothing switch | The toggle exists (Step 3I); finer redaction has no demo value on a synthetic dataset | Extend the tracing adapter's capture mode with per-field masking rules |
| 13 | Access scale | Single organization, single user, no rate limiting, no multi-tenancy | Org/role model, per-tenant isolation, rate limits, quotas | PRD lists multi-tenant infrastructure as a non-goal | Covered by the PRD's P2 roadmap |
| 14 | Crash-window storage orphans | A process crash between a manual WAV's storage write and its database commit orphans a UUID-keyed private object that no record references; live-failure compensation deletes are handled, the crash window is not | A bucket-versus-database reconciliation sweep that lists unreferenced objects and deletes or reports them | The failure direction is safe (orphan file, never a record pointing at missing audio), objects are private, and the window is milliseconds wide at demo traffic | Add a reconciliation management command (or scheduled task) comparing storage keys against `CallRecording.storage_key` |
| 15 | Stale-sweep double spend | The stale-job sweep keys on processing start age (no heartbeat column); a slow-but-alive worker swept past the threshold can cause one concurrent duplicate provider call, which the generation fence keeps out of canonical state | A heartbeat/lease column so the sweep distinguishes alive-but-slow from dead workers | The window requires a provider call slower than the generously sized threshold; the cost of one duplicate call is cents | Add a heartbeat column updated between pipeline stages and include it in the sweep predicate |
